# App Review API·앱·알림 연결 — 2026-10-20

**최신 운영 상태:** DB 적용과 잠긴 기본 검수 계정 준비를 완료했다. [실제 적용 기록](app-store-review-db-apply-20261020.md)을 참고한다. 심사 로그인은 OFF이고 통합 웹 배포는 후속 단계다.

상태: 로컬 구현과 격리 검증 완료. 운영 DB 적용·검수 계정 생성·배포·새 빌드·심사 제출은 하지 않았다.

## 연결한 경로

- 심사 로그인: 고정 `tour` / `deletion` 계정 중 하나만 서버에서 선택한다. 이메일·사용자 ID·역할 입력은 거절한다. 일반 로그인은 카카오·Apple 그대로다.
- Auth가 검증한 사용자, 서버의 고정 ID, trusted `app_metadata` 표시, Parent/탈퇴/휴대폰 확인, 본인 전용 DB 허용 목록이 모두 맞아야 세션을 반환한다. DB RPC 부재·오류·빈 허용 목록이면 차단한다.
- `/api/native/review-catalog/[...path]`: Bearer 인증 후 허용된 비공개·미종료 데모 수업만 조회한다. 일반 `/api/native/catalog`의 공개 조건은 유지한다. 비공개 행의 서비스 조회는 Auth와 DB 허용 목록을 확인한 뒤에만 시작한다.
- 홈·목록·학원·수업 상세와 progressive summary/availability 응답은 기존 표시 투영을 재사용한다. 다른 수업/학원은 상세 조회 전에 거절한다. 실제 운영자 전화번호·직원 연락처·다른 학원의 평가 집계는 검수 응답에 넣지 않는다.
- 신청은 기존 동의·자녀 소유권·학년·정원·마감·24시간 제한을 사용한다. INSERT는 검증한 사용자의 JWT로 수행한다. 검수 예외를 위해 서비스 역할로 대리 신청하지 않는다. 검수 수업과 직접 연결되지 않은 교사 공용 일정은 제외한다.
- 등록부에 의한 계정/허용 연결이 중지되면 기존 세션도 Parent API 접근이 중지된다. 탈퇴 정리 경로는 기존 인증·탈퇴 절차를 유지한다.
- 앱 카탈로그는 검수 계정에서만 인증된 전용 주소를 호출한다. 계정·로그아웃·검수 토큰 변경 때 메모리 캐시와 진행 중 응답을 무효화한다. 화면도 캐시 소유권 변경을 구독한다. 검수 데이터는 디스크에 저장하지 않는다.

## 알림

`get_app_store_review_notification_policy(application_id)`가 정확히 `normal`인 경우에만 전송한다. `suppress`·`unknown`·비정상 응답·조회 오류는 발송 허가가 아니다.

직접 진입점까지 확인한다:

- Parent 알림 wrapper, 직접 Alimtalk
- Parent·Teacher SMS 기록/발송 함수
- Teacher·Admin Studio 알림 함수
- 일정 확정·리포트/일정 변경/의견 요청 Push worker의 claim 후, 기기 조회·공급자 호출·fallback 전

발송 제한 조회가 실패해도 안전 wrapper는 업무 저장 성공을 뒤집지 않는다. 기존 푸시 재시도·중복 방지·fallback 정책을 변경하거나 전역 발송 설정을 끄지 않았다.

## 반드시 지킬 운영 적용 순서

**코드를 DB보다 먼저 배포하면 안 된다.** 새 정책 RPC가 없으면 일반 알림도 안전을 위해 전송을 중단한다. 이는 권한 조회 실패 시 보내지 않는 설계의 결과다.

1. 별도 승인 후 DB 초안을 빈 등록부 상태로 적용하고 서비스 전용 정책 RPC·권한·일반 신청의 `normal` 응답을 확인한다.
2. 검수 로그인/fixture 준비 설정은 OFF인 채 통합 코드를 배포한다. 일반 고객 회귀와 실제 신규 배포의 Apple 설정 적용을 확인한다.
3. 별도 승인된 정확한 ID로 Parent 2개와 데모학원 가상 데이터만 준비한다. 고객 계정·기존 데모 계정 비밀번호는 사용하거나 바꾸지 않는다.
4. DB 등록부와 계정 허용 목록이 일치하는지, 실제 검수 신청에 외부 알림이 없는지 확인한다. 그 뒤 준비 완료/로그인 설정을 활성화한다.
5. 새 앱을 빌드·설치해 두 계정, 신청/취소, 리포트 사진/의견, Apple 재인증·탈퇴를 실기기로 검증한다. 일반 계정도 회귀 확인한다.

필수 서버 설정 이름(값은 문서·Git에 저장하지 않음):
`APP_REVIEW_ACCESS_ENABLED`, `APP_REVIEW_FIXTURES_READY`, `APP_REVIEW_LOGIN_EMAIL`, `APP_REVIEW_PARENT_ID`, `APP_REVIEW_DELETE_LOGIN_EMAIL`, `APP_REVIEW_DELETE_PARENT_ID`.

DB 초안: `docs/sql/drafts/20261020120000_app_store_review_isolation.sql`

SHA-256: `c353f3ed4a769eeb34e5e1552adbfb052d5226b731896baeff80be538c184c03`

이번 API 연결에서 SQL 원문을 수정하지 않았다. 초안 작성 승인과 실제 DB 적용 승인은 별개다.

## 검증 결과

- DB: 실제 SQL 본문을 실행한 PGlite 격리 검사 28묶음 통과. 운영 쓰기·외부 발송 0.
- API/알림: 실제 TS 모듈로 Auth·본인 RPC·허용 목록·비공개 카탈로그·알림 진입점 14묶음 통과. 공급자는 모의 경계로 대체.
- 예약 어댑터: 실제 함수를 AST로 골라 실행한 8묶음 통과. 인증 선행, 직접 연결 일정, 정원, 숨김·마감, 휴무, 이전 교사 공용 fallback 제외를 확인.
- 심사 로그인 9묶음, 신청 18시나리오 통과. 두 고정 계정 선택, 임의 계정 입력 거절, 검수 신청의 기존 동의/정원/대상 제한 포함.
- 기존 일정 확정 푸시 16묶음, 이벤트 푸시 14묶음 통과. 기존 검사에서는 정책 경계를 `normal`로 두고 기존 전송 흐름을 확인했고, 별도 API 검사에서 실제 정책 모듈의 차단을 확인했다.
- Apple 서명·폐기 18묶음, 탈퇴 통합 17묶음, 기존 OAuth 회귀 통과. 실제 Apple 호출/계정 삭제는 하지 않았다.
- 앱 전체 202/202, 웹·앱 타입 검사/lint, 웹 운영 빌드, 두 저장소 diff-check 통과.
- 운영 빌드는 가상 Supabase 설정으로 수행했다. 비밀 환경변수 파일을 복사하거나 배포하지 않았다.

## 남은 검증

운영 DB 적용 후 권한·스키마 확인, 실제 독립 PostgreSQL 연결의 revoke/disable 경합, 검수 계정/가상 데이터 준비, 로그인한 실제 화면과 실기기 저장·취소·탈퇴 E2E는 남아 있다. 기존 단일 연결 PGlite 결과를 실제 동시성 검증으로 표시하지 않는다.

현 설치본에는 이 로컬 변경이 들어 있지 않다. 운영 전체 알림이 검수와 무관하게 정상인지도 배포 후 확인해야 한다.
