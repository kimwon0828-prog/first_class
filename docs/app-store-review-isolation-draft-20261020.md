## DB 변경 범위

새 비공개 등록부 3개는 모두 빈 상태로 생성됩니다. 앱 심사 계정을 새로 만들거나 켜지 않습니다.

| 대상 | 역할 |
|---|---|
| `app.app_store_review_parents` | 지정 검수 Parent를 등록. `enabled` 기본값 false. Auth 삭제 시 등록부만 함께 정리 |
| `app.app_store_review_classes` | 첫수업 데모학원 소속의 새 비공개 수업만 등록. 기존 신청이 있는 수업은 등록 불가 |
| `app.app_store_review_grants` | 검수 Parent와 허용 수업을 명시적으로 연결 |

등록부는 anon/authenticated에 공개하지 않습니다. 서비스 역할에도 수업 등록부 삭제 권한을 주지 않아 과거 검수 알림의 차단 표시가 실수로 없어지지 않게 합니다. 수업이 정식 생명주기 경로로 삭제되면 그 등록부는 FK를 통해 정리됩니다.

검수 Parent는 서버가 설정한 `auth.users.raw_app_meta_data.app_store_review`의 JSON boolean true, Parent 역할, 학원 소속 없음, 선생님 연결 없음, 탈퇴 진행 중 아님을 모두 만족해야 합니다. 이메일 도메인, 수업명, 클라이언트 user_metadata, 임의 session flag는 권한 근거가 아닙니다. 기존 신청이 있는 계정을 검수 계정으로 등록할 수 없습니다.

## 조회·신청 제한

- 기존 정책을 수정하거나 삭제하지 않고 검수 전용 SELECT 정책과 restrictive 정책을 추가합니다.
- 일반 계정·익명 사용자의 기존 공개 조회는 유지합니다. 검수 계정의 클래스/일정 조회는 본인에게 연결된 비공개 데모 수업으로 좁힙니다.
- 검수 계정이 실제 학원 수업을 신청하거나, 일반 계정이 검수 전용 수업을 신청하는 것은 RLS와 트리거에서 모두 거절합니다.
- 서비스 역할을 통한 실수도 검사합니다. 고객 신청을 검수 데이터로 옮기거나 검수 신청의 학부모·수업·자녀를 고객 데이터로 옮기는 것을 막습니다.
- 등록된 검수 수업을 공개하거나 다른 학원으로 옮길 수 없습니다. 종료된 수업의 신규 신청은 그대로 금지합니다.
- 기존 동의/신청 초기 상태, 본인 자녀, 배정 선생님, 휴대폰 인증, 실제 회차 일치, 정원, 마감, 날짜별 마감, 24시간 전 신청 제한을 유지합니다. 시각 검사는 기존 Asia/Seoul 규칙을 사용합니다.
- 계정 비활성화·허용 연결 회수 시 신규 신청은 중단됩니다. 이를 이유로 일반 수업 신청 권한으로 전환되지 않습니다.

기존 함수 4개를 정확한 기준 본문과 대조한 뒤 대체합니다. 서명·소유자·실행 권한·search_path는 유지합니다.

| 함수 | 변경 |
|---|---|
| `app.valid_parent_application_initial_context` | 비공개 수업 예외를 검수 Parent/허용 수업의 일치에만 허용 |
| `public.lock_class_schedule_application` | 같은 좁은 예외. 수업 잠금·종료·회차 일치 검사는 유지 |
| `app.enforce_date_booking_application` | 같은 좁은 예외. 정원·마감·시각 등 나머지 본문 유지 |
| `public.claim_parent_feedback_reminders` | 검수 신청을 기존 문자/알림톡 리마인더 후보에서 제외 |

적용 전 본문 지문이 다르거나 기존 RLS가 꺼져 있으면 트랜잭션을 중단합니다. 기존 trusted review 표시가 있는 Auth 계정이 있으면 별도 감사를 요구하고 중단합니다. 기존 계정이나 수업을 자동으로 편입하지 않습니다.

## 알림과 탈퇴

일정 확정·변경·리포트 도착·의견 요청의 검수 푸시 작업은 기존 `test_suppressed` 상태로 저장합니다. 대기열 소유권과 `suppress_legacy=true`를 유지하므로 미발송을 이유로 중복 SMS fallback을 시작하지 않습니다. 검수 작업을 pending/fallback 상태로 되돌리거나 전송 시도 토큰을 넣어도 다시 차단합니다. 실제 전송 완료인 것처럼 `sent_at`을 만들지 않습니다.

일반 신청은 기존 `all/test/off` 설정과 기존 대기열 동작을 유지합니다. 전역 푸시 설정은 수정하지 않습니다.

기존 회원탈퇴 RPC의 `parent_id=null, child_id=null` 정리 순서를 허용합니다. Auth/Parent 등록부가 삭제되어도 클래스 등록부가 남아 과거 검수 신청의 알림 차단이 유지됩니다. 이 검증은 기존 탈퇴의 detach 순서에 대한 것이며 실제 Auth·Storage 삭제 E2E를 대신하지 않습니다.

**DB 초안만으로 직접 HTTP 발송까지 차단되었다고 볼 수 없습니다.** 새 서비스 전용 RPC `get_app_store_review_notification_policy(application_id)`는 `normal/suppress/unknown`을 돌려줍니다. 서버의 Parent·Studio 알림 wrapper가 외부 공급자 요청 전에 이를 확인하도록 연결해야 합니다. `unknown`이나 조회 실패는 발송 허가가 아닙니다. 이 연결 전에는 운영 검수 데이터 생성·로그인 활성화를 하지 않습니다.

본인 전용 RPC `get_my_app_store_review_access()`는 활성화 여부와 본인에게 허용된 수업 ID만 반환합니다. 다른 사용자 ID를 넘길 수 없고 anon은 실행할 수 없습니다.

## 후속 연결과 적용 조건

1. 서버 심사 로그인은 환경변수뿐 아니라 본인 전용 DB RPC의 활성 상태도 확인해야 합니다. 운영 설정은 아직 OFF입니다.
2. 현재 공개 카탈로그/신청 어댑터는 `is_active=true`를 요구합니다. 인증된 검수 세션에 한해 승인된 비공개 클래스만 읽는 경로를 연결해야 합니다. 공개 API의 필터를 전역 완화하지 않습니다.
3. 앱 카탈로그 캐시는 일반 공개/검수 계정 사이에서 공유하지 않도록 분리·폐기해야 합니다. query parameter로 검수 역할을 선택할 수 없게 합니다.
4. 직접 Parent·Studio 문자/알림톡 및 우회 발송 경로에 서비스 전용 정책 판정을 연결하고, 모의 공급자 호출 0건 검사를 마칩니다.
5. 변경 코드를 검증·배포할 순서를 검토한 뒤 정확한 SQL 해시로 운영 적용 승인을 받습니다. 이번 초안 승인은 운영 적용 승인이 아닙니다.
6. 이후 별도로 검수용·탈퇴용 Parent 2개와 가상 데이터 생성 계획을 확정합니다. 기존 고객/데모 계정의 비밀번호를 바꾸지 않습니다. 일반 로그인은 카카오·Apple만 유지합니다.
7. 실기기·심사 안내·지원/개인정보 자료를 확인하고 마지막에 App Review 제출 승인을 받습니다.

되돌릴 때도 우선 검수 로그인과 계정 허용을 중단하고 추가 DB 보호는 유지하는 방식을 사용합니다. 과거 검수 신청이 남아 있는데 등록부나 차단 장치를 제거하는 자동 rollback은 제공하지 않습니다.

- 새 테이블은 빈 상태, 기존 샘플 데이터·정책·함수 권한은 불변임을 확인했습니다. 기존 기준과 다른 함수/RLS/검수 표시가 있으면 변경 전 중단되는 것도 확인했습니다.
- 단일 연결 PostgreSQL/WASM이므로 독립된 두 실제 연결의 경합은 검증하지 않았습니다. revoke/disable과 신청을 직렬화하는 행 잠금은 구현했지만, 운영 적용 전에 별도 실제 PostgreSQL 동시성 확인이 남습니다.
- 운영 DB·실제 계정·실기기·실제 알림 공급자를 사용한 검증은 하지 않았습니다.
